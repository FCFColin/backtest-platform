## 2. 事件分类与处置流程

### 2.1 数据库故障（PostgreSQL 不可用）

**症状**: API 返回 503，健康检查 `GET /api/health` 数据库状态为 `down`

**处置步骤**:

1. 确认数据库进程状态：`docker exec backtest-postgres pg_isready`
2. 检查连接池：`pg_stat_activity` 查看连接数
3. 若主库不可恢复 → 启动从备份恢复：
   ```bash
   bash scripts/backup-restore.sh LATEST
   ```
4. 若只读副本可用 → 确认降级模式（`getReadClient()` 自动降级到主库）
5. 恢复后验证数据完整性，通知用户

**关联文档**: `docs/compliance/backup-restore.md`

### 2.2 Redis 不可用

**症状**: 认证/会话/限流功能降级

**处置步骤**:

1. 确认 Redis 进程：`docker exec backtest-redis redis-cli ping`
2. 若 Sentinel 触发故障转移 → 等待自动切换（< 30 秒）
3. 若全部 Redis 不可用 → 确认降级：
   - 认证降级到 in-memory（单实例）
   - 限流降级到内存计数器
4. 通知多实例部署需注意会话不一致

### 2.3 引擎服务不可用（engine-go）

**症状**: 回测/MC/优化器 API 返回 503 + Retry-After

**处置步骤**:

1. 确认引擎健康：`curl http://localhost:5004/api/engine/health`
2. 检查引擎日志：`docker logs backtest-engine-go`
3. 重启引擎：`docker compose restart engine-go`
4. 若持续不可用 → API 返回 503 fail-closed（ADR-031），不使用降级计算
5. 通知用户引擎维护中

### 2.4 密钥泄露

**症状**: gitleaks 检测到密钥 / 审计日志异常 / 人为发现

**处置步骤**:

1. **立即轮换泄露的密钥**（JWT 密钥 / API Key / 数据库密码 / MinIO 凭证）
2. 撤销所有活跃 session（清空 Redis 中的 refresh token）
3. 审查泄露时间窗口内的审计日志，确认是否有未授权操作
4. 提交安全事件报告
5. 加强密钥管理（迁移至 K8s Secret / Vault）

### 2.5 DDoS / 恶意流量

**症状**: 请求量异常飙升 / API 响应延迟增加

**处置步骤**:

1. 确认限流是否生效：检查 `rateLimiter` 指标
2. 启用 IP 封锁：在 APISIX/Nginx 层添加恶意 IP 黑名单
3. 通知云厂商启用 DDoS 防护
4. 若服务不可用 → 临时关闭非核心端点

## 3. 事后审查

### 3.1 事件报告

每次 P0/P1 事件后 48 小时内提交事后报告，包含：

- 事件时间线（发现 → 响应 → 恢复）
- 影响范围（用户数/数据/功能）
- 根因分析
- 改进措施与跟踪计划

### 3.2 复盘机制

- P0 事件：全员复盘会议（48 小时内）
- P1 事件：技术团队复盘（1 周内）
- 改进措施录入 GitHub Issues 跟踪
