## 1. 访问控制模型

### 1.1 RBAC 角色体系

本平台采用基于角色的访问控制（RBAC），定义 3 个内置角色 + 自定义角色：

| 角色        | 权限范围                                                        | 适用对象          |
| ----------- | --------------------------------------------------------------- | ----------------- |
| **admin**   | 全部 7 项权限（用户管理/数据管理/回测/分析/优化/计费/系统设置） | 组织管理员        |
| **analyst** | 回测 + 分析 + 优化（4/7 权限）                                  | 投研人员          |
| **viewer**  | 只读查看（1/7 权限）                                            | 合规审计/外部顾问 |

> 自定义角色通过 `rbacRoutes.ts` API 创建，分配任意权限组合。

### 1.2 权限矩阵

| 权限                | admin | analyst | viewer |
| ------------------- | ----- | ------- | ------ |
| `user:manage`       | ✅    | —       | —      |
| `data:manage`       | ✅    | —       | —      |
| `backtest:execute`  | ✅    | ✅      | —      |
| `analysis:execute`  | ✅    | ✅      | —      |
| `optimizer:execute` | ✅    | ✅      | —      |
| `billing:manage`    | ✅    | —       | —      |
| `system:config`     | ✅    | —       | —      |

## 2. 多租户数据隔离

### 2.1 PostgreSQL RLS

- **机制**: Row Level Security（行级安全策略），每行数据附带 `tenant_id`
- **强制点**: `pool.ts` `withTenant()` 在事务级 `SET LOCAL app.current_tenant_id`
- **策略**: 用户仅能查询/修改所属组织的行，跨组织访问被数据库层拒绝

### 2.2 租户上下文生命周期

```
请求到达 → JWT 提取 orgId → withTenant(orgId, fn) → SET LOCAL → RLS 生效 → COMMIT → 自动清除
```

- PgBouncer transaction-pooling 兼容（`is_local=true`，随事务结束自动复位）
- 副本角色须为 `NOBYPASSRLS`，防止绕过策略

## 3. 认证机制

### 3.1 JWT + Refresh Token

| 参数              | 值                           | 说明                              |
| ----------------- | ---------------------------- | --------------------------------- |
| Access Token TTL  | 15 分钟                      | 短期 token，减少泄露窗口          |
| Refresh Token TTL | 7 天                         | 长期 token，用于轮换 access token |
| 轮换策略          | 每次刷新生成新 refresh token | 旧 token 加入黑名单（Redis）      |
| 算法              | RS256（生产）/ HS256（开发） | 私钥签名，公钥验证                |

### 3.2 API Key（组织级）

- **用途**: 服务间认证 / 程序化 API 调用
- **存储**: SHA-256 哈希存储（ADR-033），明文仅在创建时返回一次
- **吊销**: 支持随时吊销，吊销后立即失效
- **审计**: 每次 API Key 认证记录审计日志

### 3.3 MFA/TOTP

- **要求**: 管理员账户强制启用 MFA
- **实现**: RFC 6238 TOTP（30 秒窗口），支持 Google Authenticator / Authy
- **备份码**: 10 个一次性备份码，用于设备丢失恢复

## 4. 密码策略

| 规则     | 要求                                          |
| -------- | --------------------------------------------- |
| 最小长度 | 12 位                                         |
| 复杂度   | 大写 + 小写 + 数字 + 特殊字符，至少各 1 个    |
| 历史限制 | 不能重用最近 5 次密码                         |
| 有效期   | 90 天（到期后强制更换）                       |
| 锁定策略 | 5 次失败锁定账户 15 分钟，10 次封锁 IP 1 小时 |

## 6. Break-Glass 操作规程

### 6.1 场景

当正常认证机制全部不可用时（JWT 密钥丢失、数据库不可用、Redis 宕机），使用 break-glass 凭证紧急访问。

### 6.2 操作流程

1. **申请**: 运维人员向技术负责人申请 break-glass 使用授权
2. **使用**: 使用 `ADMIN_API_KEY` 环境变量作为静态凭证认证
3. **记录**: 所有 break-glass 操作自动记录审计日志（标记 `break_glass: true`）
4. **审查**: 使用后 24 小时内提交事后审查报告
5. **轮换**: 每次使用后轮换 `ADMIN_API_KEY`

### 6.3 限制

- `ADMIN_API_KEY` 不可吊销（平台 break-glass 凭证）
- 仅限紧急运维使用，日常操作禁止使用
- 须严格保管，最小化知悉范围
