# ADR-013: OpenAPI 契约扫描器的实现适配策略

| 状态 | 已接受 | 日期 | 2026-08-24 | 关联 | ADR-008, DADR-052 |

## Context

`tests/contract/api-implementation.contract.test.ts` 以正则扫描路由源码，双向校验 spec↔实现一致。
authRoutes.ts 重构为表驱动注册（ROUTES 数组 + `router[method]` 循环）后，字面量
`router.get('...')` 正则失明，8 条真实存在的路由被误判缺失（contract 14→13）。

修复（commit daf33f7f）为扫描器新增行首元组识别。本 ADR 记录该变更的定性：
**契约语义（spec↔实现双向一致）未动，变更是验证器对实现形态的检测适配**——
但按 R-05 v2 修订版，验证器实现变更同样留痕于此。

## Decision

1. 已落地：表驱动注册的行首元组正则（依赖 prettier printWidth 保证元组独占一行）。
2. 已知局限【推断】：元组被提取为常量引用、或多元组折叠单行时将静默漏检；
   金丝雀夹具只能捕获注释类失效，不能捕获间接引用失效。
3. 终局方案：以运行时枚举替换源码正则——动态 import 路由模块
   （vi.mock redisClient/pg 阻断副作用），手写 Express 4 router.stack walker，
   断言 spec ⊆ 枚举结果。落地后删除全部源码正则（约 −90 行），
   并使"任何未来注册模式"天然可测。金丝雀夹具随终局方案常驻 contract 套件。

## Consequences

- 短期：双正则并存，漏检风险由金丝雀部分兜底。
- 长期：正则债务类别清零；Express 5 迁移时 walker 属第一现场报警点。
