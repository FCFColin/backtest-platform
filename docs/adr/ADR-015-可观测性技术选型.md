# ADR-015: 可观测性技术选型（OTel + Pino + prom-client，SaaS 后端）

> **企业理由**：多语言微服务架构下，结构化日志、指标、追踪三支柱的统一方案是跨服务排障、性能分析与故障定位的基础能力。自建 Collector 对小规模团队运维负担过重，SaaS 后端通过标准 OTel 环境变量实现供应商无锁定切换。

## Context

系统需要结构化日志、指标采集、分布式追踪三支柱可观测性。Node.js/Go 服务需要统一方案。原定自建 OTel Collector 架构要求团队自建并运维 Collector 实例，对小规模团队是显著运维负担。同时 engine-go 与 data-fetcher 各自维护 100% 相同的 OTel 初始化代码（~70 行），违反 DRY。

## Decision

- **日志**：pino（Node.js）+ slog（Go）— 结构化 JSON 输出（pino 选型详见 ADR-053）
- **指标**：prom-client（Node.js）+ prometheus/client_golang（Go）— Prometheus 格式直连
- **追踪**：OpenTelemetry SDK（两语言统一）— W3C Trace Context 传播
- **DB 追踪**：@opentelemetry/instrumentation-pg — 自动为 pg 查询创建 span
- **Trace 导出**：通过标准 OTel 环境变量（OTEL_EXPORTER_OTLP_ENDPOINT + OTEL_EXPORTER_OTLP_HEADERS）直接导出到 SaaS 后端（Honeycomb/Datadog/Axiom），**移除自建 Collector**。指标仍走 Prometheus 直连，不走 SaaS。未设置端点时 trace 仅进程内（无导出），适合本地开发。
- **Go 共享 module**：抽取 packages/go-shared/observability/otel.go 作为单一权威实现，engine-go 与 data-fetcher 通过 replace 指令引用。同时抽取 pprof/http.Server/slog/securityHeadersMiddleware 到 go-shared。

## Consequences

- (+) 两语言统一 OTel 标准，跨服务 trace 可串联
- (+) SaaS 切换灵活，通过环境变量即可在供应商间迁移，无供应商锁定
- (+) 移除自建 Collector 运维负担（部署、升级、容量规划、故障排查）
- (+) 削减 ~70 行跨服务重复 OTel 代码 + ~44 行 pprof/slog/httpServer 重复代码
- (+) 本地开发体验改善：不设置端点即跳过导出，无需启动 Collector
- (-) OTel SDK 增加约 5MB 依赖和微秒级开销
- (-) SaaS 后端外部依赖：供应商可用性影响 trace 可观测性；跨网络导出需注意 PII 过滤
- (-) enhancedDatabaseReporting 需配合采样避免高基数
- (-) engine-rs（已删除）的 tracing/metrics 不再适用——Go 引擎为唯一计算后端（ADR-031）
