# ADR-016: 弹性策略（熔断器 + 限流 fail-closed 分级）

> **企业理由**：微服务架构中下游服务故障若不快速失败将引发级联雪崩，熔断器是保障系统整体可用性、实现故障隔离的关键机制。限流的失败模式（Redis 不可用时放行还是拒绝）是安全与可用性的根本权衡——一刀切 fail-open 会让攻击者通过制造依赖抖动绕过所有限流。

## Context

微服务架构中，下游服务不可用时需快速失败避免级联故障。不同服务（Go引擎、PostgreSQL、Go数据服务）需独立熔断。同时所有限流器曾统一使用 passOnStoreError: true（Redis 不可用时放行），攻击者只需令 Redis 短暂不可用即可绕过登录限流进行暴力破解、绕过 compute 限流发起资源耗尽型 DoS。

## Decision

### 1. 熔断器

- Node.js 服务：opossum 熔断器（Go引擎、PostgreSQL 各独立实例）
- Go 服务：sony/gobreaker（BaoStock API 熔断）
- 熔断器配置：50% 失败率触发 Open，10s 后 HalfOpen 探测
- PostgreSQL 熔断器替代 dbAvailable 布尔标记，提供自动恢复能力

### 2. 限流 fail-closed 分级策略

按端点风险分级设定故障策略：

- /api/v1/auth/login、/auth/refresh：fail-closed（暴力破解/重放是直接攻击面）
- compute（/api/v1/backtest、/backtest-optimizer）：fail-closed（资源耗尽 DoS，CPU/内存代价高）
- 全局 apiLimiter（只读 API）：fail-closed（Redis 抖动可绕过全局配额滥用 /data；与敏感端点策略对齐）
- adminLimiter、data/manage：fail-open（已由 jwtAuth + RBAC 前置保护，限流为纵深防御非唯一防线）

全局 apiLimiter.passOnStoreError 设为 false，Redis 不可用时返回 429/503 而非无限放行。

## Consequences

- (+) 自动恢复能力，避免 dbAvailable=false 后需人工重启
- (+) 消除"抖动绕过限流"攻击路径；安全敏感端点在依赖故障时安全地降级（拒绝）
- (+) 全局限流与敏感端点策略一致，纵深防御完整
- (-) 熔断器状态机增加调试复杂度；HalfOpen 探测请求可能失败导致反复熔断
- (-) Redis 故障期间登录/计算/只读 API 均不可用——这是刻意的安全权衡，且 Redis 应有 Sentinel 高可用（ADR-018）
- (-) fail-closed 触发的 503 应纳入 SLO 错误预算并告警（区别于业务 429）
- (-) 纵深防御（jwtAuth 已保护的 admin/manage 端点保留 fail-open）避免过度牺牲可用性
