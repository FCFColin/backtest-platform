# ADR-047: 后端模块化策略

## 状态：已接受

## 日期：2026-07-26

## 上下文

`packages/backend/src` 当前是单一 Node.js 包，内部按 DDD 分层（domain/application/infrastructure/routes）。
随着功能增长，编译速度会持续下降，且无法按模块独立部署。
现阶段不需要实际物理拆分，但需要明确逻辑边界和触发条件，避免模块间耦合无序增长。

## 决策

### 当前状态

`packages/backend` 是单一 Node.js 进程，内部按 DDD 分层。不进行物理拆分，但明确逻辑边界。

### 逻辑边界（7 个模块）

| 模块                | 职责               | 文件归属                                                                                                                                                                                |
| ------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **auth-module**     | 认证/授权/用户管理 | `routes/authRoutes.ts`, `application/auth/*`, `middleware/authShared.ts`, `middleware/jwtAuth.ts`, `middleware/rbac.ts`, `middleware/refreshToken.ts`, `middleware/tokenRotation.ts`    |
| **backtest-module** | 核心回测调度       | `routes/backtestRoutes<area>.ts`, `application/backtest-service.ts`, `queues/backtestQueue.ts`, `queues/worker.ts`                                                                      |
| **billing-module**  | Stripe 计费        | `routes/billingRoutes.ts`, `application/billing/*`                                                                                                                                      |
| **data-module**     | 数据管理与查询     | `routes/dataRoutes.ts`, `routes/dataManageRoutes.ts`, `infrastructure/dataQuery.ts`, `infrastructure/dataFacade.ts`, `infrastructure/tickerDataService.ts`, `queues/dataUpdateQueue.ts` |
| **org-module**      | 组织与成员管理     | `routes/orgRoutes.ts`, `application/org/*`                                                                                                                                              |
| **admin-module**    | 平台管理           | `routes/adminRoutes.ts`, `routes/adminKeyRoutes.ts`, `routes/rbacRoutes.ts`, `routes/auditRoutes.ts`, `routes/featureFlagRoutes.ts`                                                     |
| **webhook-module**  | Webhook 投递       | `routes/webhookRoutes.ts`, `application/webhookService.ts`, `queues/webhookQueue.ts`                                                                                                    |

### 模块间通信规则

- **当前**：模块间直接函数调用（同一进程内）
- **拆分后**：改为 HTTP + BullMQ 异步消息
- **共享状态**：Redis（已有，用于缓存/队列/会话）
- **数据库**：当前共享 PostgreSQL，拆分后评估是否需要独立 Schema

### 拆分触发条件

当满足以下**任意一条**时，评估该模块是否应独立部署：

1. **部署频率差异**：该模块的部署频率远高于其他模块（每周 > 5 次独立部署）
2. **资源竞争**：该模块的 CPU/内存消耗导致其他模块延迟
3. **团队并行**：团队规模超过 10 人，多团队并行开发该模块
4. **扩缩容策略差异**：该模块需要与其他模块不同的扩缩容策略（如计算密集 vs IO 密集）

### 技术准备

- 模块间通信：当前直接函数调用，拆分后改为 HTTP + BullMQ
- 共享状态：Redis（已有）
- 数据库：当前共享 PG，拆分后评估是否需要独立 Schema
- 可选：引入 `dependency-cruiser` 检测模块间非法依赖（如 billing 不应直接导入 backtest 的 Repository）
- 可选：为每个逻辑模块创建 `index.ts` 作为公开 API 边界

## 后果

- **正面**：明确的逻辑边界防止模块间耦合无序增长
- **正面(10**：量化触发条件使拆分决策有据可依，避免"感觉应该拆了"的主观判断
- **正面**：模块间通信规则提前约定，拆分时迁移路径清晰
- **负面**：模块边界靠约定维持，无工具强制（除非引入 dependency-cruiser）
