# ADR-004: 领域模型重构策略（渐进式 DDD）

> **企业理由**：贫血模型导致业务逻辑散落、规则重复、耦合严重，渐进式 DDD 重构可在控制风险的前提下统一业务规则、提升可维护性。

## Context

当前系统使用贫血模型，业务逻辑散落在路由和服务文件中：6 个完整算法嵌入路由文件；shouldRebalance 在 3 处重复实现；缺乏领域边界，回测参数校验、策略执行、结果耦合在同一服务层；新增策略需修改多个文件违反开闭原则。

## Decision

采用渐进式 DDD 落地策略，按 Value Object → Aggregate → Domain Event 的顺序分阶段重构：

1. **Phase 1 - Value Object**：提取回测参数（BacktestParams）、策略配置（StrategyConfig）、组合权重（PortfolioWeight）等值对象，封装校验逻辑和不变式
2. **Phase 2 - Aggregate**：定义回测聚合根（BacktestSession/Run），统一 shouldRebalance 等业务规则，划定事务边界
3. **Phase 3 - Domain Event**：引入领域事件（BacktestCompleted、RunStarted/Completed/Failed/Cancelled），解耦副作用（通知、审计、缓存更新），为 Outbox 模式（ADR-005）提供事件源

放弃革命式重构（风险不可控，生产系统长时间不可用不可接受）；放弃不重构（技术债持续累积）。

## Consequences

- (+) 渐进式可逐步验证每个阶段的正确性，降低回滚成本
- (+) Value Object 是最安全起点——纯值校验无副作用，可独立测试
- (+) Aggregate 阶段统一业务规则，消除重复逻辑
- (+) Domain Event 解耦副作用，为 Outbox 提供事件源
- (-) 渐进式意味着长期新旧架构并存，增加认知负担

## 实施状态

- Phase 1（Value Object）：已完成——domain/value-objects/ticker.ts、weight.ts 已落地
- Phase 2（Aggregate）：部分完成——Portfolio 充血模型（fromDTO 工厂 + validateWeightSum 不变量）已落地；**Run 聚合根已于 2026-08-13 退役**（worker 直接落库 backtest_runs，状态机由 DB 列 + worker 进度管理，见 ADR-012/ADR-013）
- Phase 3（Domain Event）：收敛——DomainEventDispatcher + allSettled 语义保留（domain/events/events.ts），但事件源仅剩审计链路（AuditEvent，见 ADR-005 现状确认）；BacktestCompleted 与 Run* 事件已随 Run 聚合一起移除
- 兼容性：DB schema 保持 pending/running/completed/failed；退役不影响该列语义
